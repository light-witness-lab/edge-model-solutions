# On-device inference runtimes (2026-10)

> 这篇横评只回答一个工程问题：一个 256–600M 的多模态 ranker（视觉 encoder + 小决策头），1–3 次/秒、30 秒预算、要求确定性 benchmark，在 2026 年的 Android/iOS 上该用什么运行时。评估维度是各段算力对应哪个后端、谁为可复现性兜底。结论：ONNX Runtime CPU/XNNPACK 作为可移植基线，llama.cpp 作为手工优化性能标尺，QNN/ExecuTorch 仅在骁龙旗舰上提供增量收益，NNAPI 与 ncnn-LLM 不进入候选。
>
> Survey, 2026-10-18. External research only — see [evidence tiers](README.md#evidence-discipline). Versions and AAR sizes below were checked against official repositories / Maven Central / Google Maven; latency figures carry their device and quantization. Nothing here is a device result of our own.

## 0. The three industry shifts that invalidate older advice

1. **NNAPI is deprecated in Android 15.** The NDK migration guide says so outright and warns future devices may fall back to CPU; custom models are directed to LiteRT (GPU delegate / unified NPU interface), GenAI to AICore. No new design should make NNAPI its primary acceleration path. <https://developer.android.com/ndk/guides/neuralnetworks/migration>
2. **TFLite is now LiteRT, and MediaPipe LLM Inference is being subsumed by LiteRT-LM** (Google I/O 2025; TF 2.20 blog, 2025-08, confirms `tf.lite` eventually leaves the TF package; pip package `ai-edge-litert`). <https://blog.tensorflow.org/2025/08/whats-new-in-tensorflow-2-20.html> · <https://ai.google.dev/edge/litert/migration>
3. **ExecuTorch 1.0 GA (2025-10-17) promoted the QNN HTP backend from beta to production-ready**; Qualcomm's QNN SDK was renamed QAIRT from 2.32 (2025-03), SNPE branding merged. <https://pytorch.org/blog/introducing-executorch-1-0/>

## 2. Critical selection for our workload

Restating the target: a 256–600M multimodal ranker (vision encoder + small decision head) on Android, 1–3 calls/s, a 30 s per-round budget, deterministic and reproducible benchmarks. This is **low-frequency, short-sequence, vision-heavy**, not long-text streaming generation — so the decode tok/s marketing column is nearly irrelevant: the 9–85 t/s spread across runtimes is dwarfed by differences in vision encode and prefill (the same conclusion as the [KV note](02-kv-and-prefix-caching.md) §5 and the P/D note's real-phone throughput table ([03 §3.2](03-prefill-decode-disaggregation.md)).

### Primary choices

1. **ONNX Runtime (CPU/XNNPACK) as baseline and production path.** (a) At ~300–350 MB of INT4 weights for a 600M stack and short sequences, a modern big-core cluster finishes in seconds — the 30 s budget has headroom; (b) op coverage for a CNN/ViT encoder plus MLP/small-attention head is the most complete and does not depend on any model-family whitelist — two subgraphs, two sessions; (c) fixed threads + fixed arena on CPU is the most cross-device reproducible option, which is what a benchmark protocol needs; (d) MIT, trivial AAR integration, existing team knowledge. Accepted hazards: MatMulNBits is 4-bit-only with optimized ARM64 kernels (block 32 is the safe setting), 8-bit weight-only goes through QDQ; do not expect anything from NNAPI EP; trim the 18.2 MB arm64 `.so` with the mobile usability checker.
2. **llama.cpp (CPU, optionally Vulkan) as the performance yardstick, not the framework.** Use Q4_K_M/imatrix, `--cpu-mask` big-core pinning, q8_0 KV to measure a "hand-optimized upper bound" and quantify what the ORT path leaves on the table. Cost: C++ edits for custom structures, no official AAR.

### Track, in priority order

1. **ExecuTorch 1.5.x + QNN HTP** — production backend, 16a4w and Qwen3-VL workflows added recently — if the 120 Hz viewfinder ever compresses budgets to tens of milliseconds and target devices concentrate on Snapdragon 8 Gen 3 / 8 Elite. The export brittleness, whitelist CPU fallback, and architecture-bound context binaries remain unsolved in 2026; not a cross-device baseline.
2. **MNN 3.6.x** — the highest-completeness Chinese stack for Qwen-VL-family models with full-LLM-on-NPU tooling; Apache-2.0, Chinese docs, default 4-thread big-core policy suits low-frequency loads; risks are the thin external ecosystem and the July-2026 maturity of its Hexagon backend.
3. **LiteRT-LM** — strong GPU/NPU numbers, but a whole-model path that cannot host our custom vision encoder; viable only if the decision head is replaced by an end-to-end Gemma-3n/Qwen-VL-class model. MediaPipe tasks-genai (42 MB AAR) is its older shell.
4. **Apple** — ORT CoreML EP to reuse the ONNX artifact if iOS ever matters; MLX Swift for pure-Swift LLM apps; Core AI's device cutoff and ANE dynamic-shape limits mean another year of watching.

### Explicitly rejected

- **NNAPI** (TFLite delegate or ORT EP): deprecated in Android 15, CPU fallback ahead, driver fragmentation with no rescue — never the primary path for new work.
- **NCNN for LLM**: transformer primitives only since 2026-01, no INT4 weight toolchain, no KV quantization, no engine layer — half a llama.cpp to write. Its CV encoder remains excellent.
- **MediaPipe LLM Inference for our model**: black box, fixed families, 26.6 MB engine `.so`, no app-level threading/affinity — conflicts with a custom multimodal ranker and reproducible benchmarks.
- **Raw QNN/Genie as the benchmark base**: architecture-bound context binaries (v75 vs v79 do not mix), NPU clock/driver variance, single-session limits — flagship uplift only, never the reproducibility floor.
- **Two ORT 4-bit traps**: MatMulNBits without optimized kernels for bits ≠ 4 on ARM64, and onnxruntime-genai's builder whitelist. For a single-token decision head the hand-written loop is small and cleaner than patching the builder.

One sentence: **ORT CPU/XNNPACK guarantees determinism, llama.cpp calibrates the ceiling, QNN/ExecuTorch provides Snapdragon-flagship uplift, MNN stays on watch for Qwen-VL-family models, and NNAPI plus ncnn-LLM are out.**

## 3. How this maps to the repository

- The pinned runtime stays **ONNX Runtime 1.22** deliberately: `scripts/d1-prompt-eval` and `scripts/inf-perf-bench` pin the same version so desktop and device comparisons share a runtime. The newer 1.31 line is recorded here, not adopted silently.
- The survey's "4-bit-only ARM64 kernel" warning is not hypothetical for us: the pinned d1 stack ships `decision_q4` precisely because the official 8-bit `decision_quantized` graph does not run on ORT 1.22 (missing accuracy_level=4 / unpacked-4-bit path) — a `loaded-only` finding already recorded in the README and [`evaluations/d1-omni-600m-pin.json`](../../evaluations/d1-omni-600m-pin.json).
- Every runtime switch in the variable matrix of [`benchmarks/inference-perf`](../../benchmarks/inference-perf/) is run behind the same W1/W2 workloads and gate-validity counters: a faster runtime that trips the margin/permutation gate is a regression, not a win.
- QNN/ExecuTorch uplift experiments, if they ever happen, ship as an *additional* backend record — model id, device, context-binary architecture, thermal state, and gate outcomes attached — never as a replacement for the CPU baseline.
